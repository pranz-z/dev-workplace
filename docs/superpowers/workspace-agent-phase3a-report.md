# Workspace Agent Phase 3A implementation report

Date: October 9, 2026. Status: implemented locally; migration and application rollout pending.

1. **Architecture.** Native Gemini read/proposal loop → server canonicalization → private durable actions → explicit selected Apply/Cancel → canonical reload, ownership locks, version check, deterministic mutation and atomic audit. Apply has no model dependency.
2. **Files changed.** Application refresh: `app/app/page.tsx`. UI: `components/ai/AgentProposalCards.tsx`, `WorkspaceAiChat.tsx`. Agent: `contract.ts`, `proposal-schema.ts`, `proposals.ts`, `registry.ts`, `schemas.ts`, `tools.ts`, `executor.ts`, `prompt.ts`, `store.ts`, `action-route.ts`, and new `schedule-summary.ts` under `lib/ai/agent`. Tests: `agent.test.mjs`, `phase2.test.mjs`, new `phase3a.test.mjs`, `phase3a-database.test.mjs`. New migration and this report complete the change set.
3. **Proposal tools.** Added `propose_reschedule_milestone({milestoneId,targetDate})` and `propose_reschedule_project({projectId,targetDate})`. Reused `propose_update_task` for due dates. Strict field whitelists reject extra fields, forged before states, invalid UUIDs and noncanonical dates.
4. **Read tools.** Added `get_calendar_load({startDate,endDate,projectId?})`: inclusive maximum 31 days, incomplete task/milestone/project counts, zero-load days, at most 1,000 scanned owned rows per type, explicit truncation. Added optional milestoneId filtering and milestone identity to task summaries to support moving a milestone's unfinished tasks. Existing 12 read operations retain their default semantics.
5. **Tasks.** Existing dueDate update supports null→date, date→date and date→null, with existing task status/priority/create behavior preserved. Proposal generation does not mutate tasks.
6. **Milestones.** Server reads canonical milestone title, parent, target date and version through an owned-parent join. Apply updates target_date only; clear uses null. Repeated proposals merge by type and identity.
7. **Projects.** Server reads the owned project and canonical target/version. Apply updates target_date only, with identity constrained to the stored parent project ID. Clear uses null.
8. **Plan my week.** Prompt requests relevant task/target reads and workload counts before distributing date proposals; it considers priority, overdue state, requested exclusions and workdays. Canonical proposals are grouped by date in the answer. Each intended task move requires its own proposal; moving a milestone does not implicitly move tasks.
9. **Timezone.** Existing Gemini adapter supplies workspace timezone and current local Calendar date. Calendar date normalization and validity helpers are reused. Next week is defined in the prompt as the following Monday–Friday. Existing Calendar thisWeek remains today–Saturday. Tests cover Manila and Los Angeles around a UTC date boundary; real-model interpretation remains a rollout acceptance item.
10. **Limits.** Ten actions, ten aggregate native calls, six rounds, existing timeout/body/quota/lease bounds remain. Reads consume the same call budget, so practical planning batches may contain fewer than ten writes. Limit errors persist no new batch.
11. **Partial results.** Every proposal answer states that only listed actions are proposed and the schedule may be partial. Observed truncated reads add an explicit partial-results notice. Model claims about completed changes are replaced by a server-generated canonical summary.
12. **Cards.** Task, Milestone and Project labels; due-date/target-date before→after display; existing selection, Apply, Cancel, pending/applied/cancelled/conflict/failed and Review again flow. Review prompts identify the correct entity. No new approval system.
13. **Refresh.** Successful Apply reloads through existing loadWorkspaceData and sets tasks, projects and milestones together. Calendar derives from those updated collections without browser reload. Failed refresh retains truthful applied status and reports refresh failure.
14. **Stale state.** Canonical expected_updated_at is compared with the locked entity version. Conflicts are terminal; no force overwrite. Parent ownership is held under a share lock for milestone writes; project writes lock the owned project row.
15. **Audit.** Extended existing action_type constraints; no new audit tables or hidden reasoning. Existing entity_id stores typed identity, inferred from action_type. Batch projection adds entityId while retaining legacy taskId compatibility. New entities use the same run/status/audit timestamps.
16. **Migration.** `supabase/migrations/20261008231753_workspace_agent_date_scheduling.sql`, generated with Supabase CLI. Applied `20261008152535_workspace_agent_task_proposals.sql` is untouched. The new migration has not been applied to production.
17. **Security.** Private RLS/table isolation remains; no browser grants. New helper is inaccessible to browser/service callers directly; new Apply RPC is service-only, SECURITY DEFINER with empty search_path and fully qualified static SQL. Save revalidates ownership/parent identity. Apply revalidates payload, ownership and version; entity write and audit commit together. Existing replacement functions retain their restricted ACLs.
18. **Tests added.** 15 Phase 3A unit/integration tests and two database tests (one static, one comprehensive disposable PostgreSQL scenario). Assertions cover strict schemas, null/date transitions, authoritative state, merges/no-ops, ownership, cap, bounded counts, completion filtering, milestone scope, timezone, grouped mixed proposals, load/partial warnings, canonical Apply dispatch and dependency guidance. Database scenario covers migration over existing Phase 2 actions, legacy task Apply, both date entities, clear, stale, repeat, cancel, foreign access, invalid payloads, ownership changes, mixed outcomes, audit rollback and role grants.
19. **Phase 3A result.** 17/17 pass, including actual PGlite execution of both migrations. Tests use an external existing PGlite installation via AGENT_TEST_PGLITE_MODULE; no dependency was added. Without that variable, the executable database case intentionally skips.
20. **Phase 2 result.** 17/17 Phase 2 unit/static/disposable-database tests pass. Only the tool-catalog expectation changed in the old unit test.
21. **Phase 1 result.** 21/21 Agent tests pass; expected read-tool count now 13. Existing Calendar tests also pass unchanged.
22. **Full suite.** 227 tests: 225 passed, zero failures, two optional portfolio CMS database cases skipped because their separate configuration was absent. Includes private AI, Public AI, task/Calendar and workspace regression checks.
23. **TypeScript.** `npx tsc --noEmit` passed. Temporary preview route caused a stale generated development validator during the first build; restarting Next development regenerated it, then validation passed.
24. **ESLint.** Changed Agent/UI/application files pass with zero warnings/errors. An unused test fixture import was removed before final checks.
25. **Build.** `npm run build` passed, including production compilation, TypeScript and static page generation. No temporary acceptance route remains.
26. **Diff.** `git diff --check` passed; Phase 2 migration has no diff. No commit, push, deploy or production schema mutation was performed.
27. **Responsive/browser acceptance.** Real WorkspaceAiChat, AgentProposalCards and WorkspaceCalendar mounted in a temporary explicit fixture with an isolated local mock HTTP backend. At 1440/1024/768/390/320 px, card scroll width equalled card client width (301/934/678/300/230 px respectively); document width stayed within viewport. Mobile screenshots showed readable wrapped titles/date diffs. Tested overdue→Friday proposal, plan-next-week mixed cards, milestone-only and project-only cards, zero fixture mutations before Apply, task/project Calendar movement after Apply, stale milestone conflict alongside task success, unselected project remaining pending, and Cancel. Temporary page/proxy and dev processes were removed/stopped. Mock response prose is fixture content, not evidence of real Gemini scheduling quality.
28. **Limitations.** Live Gemini planning and production Supabase acceptance were deliberately not run. Scheduling is model-guided, date-only and bounded, not an availability solver. Load warnings are advisory existing counts (not a prediction of final occupancy) and may be truncated. Dependency warnings in canonical summaries cover proposed targets and related proposed tasks; the prompt also asks Gemini to consider existing deadlines. Full authenticated production refresh is wired through the existing loader; browser refresh acceptance used mocked fixture state. Public AI, Chat request/prompt behavior, Calendar helpers, Drive and GitHub were not changed.
29. **Rollout.** Review the new migration and diff, confirm migration history matches deployed Phase 2, rehearse the new migration in staging, then apply it through the normal approved migration workflow before releasing this application change. Verify existing task approvals plus project/milestone date proposals, clear dates, selected mixed Apply, stale conflicts, cross-user denial, browser RPC denial and timezone/Calendar refresh with a real account. Production rollout requires a separate explicit request. Existing service credentials/configuration remain required; no new environment variables.
30. **Phase 3B handoff.** Keep this date-only approval/audit path intact. Design time blocks separately with explicit timezone, start/end semantics, availability/conflict policy, storage and narrow proposal/Apply tools. No hourly events, focus persistence, external Calendar integration or autonomous Apply has been introduced here.
