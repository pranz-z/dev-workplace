## Requested 32-point report

1. **Ambiguity root cause.** The system prompt required clarification, but update/cancel tools accepted a model-supplied owned block UUID without resolving it against the human request. Ownership alone could not distinguish two plausible targets.
2. **Ambiguity fix.** Added a deterministic resolver against canonical owned rows. It considers local date/range intersections, title tokens/full titles, linked task/project labels, source time and cancelled status. Explicit block UUIDs use an owned exact lookup. Reads are bounded to 501 rows; at most five candidate summaries are returned. A truncated scan cannot establish a unique textual match. Ambiguous requests return clarification before Gemini runs. Proposal collection independently checks that the model ID equals the resolved ID. Pronouns may inherit only the latest unambiguous human reference, revalidated against DB state; assistant-selected IDs do not resolve ambiguity.
3. **Duration-preservation root cause.** Update patches accepted both start and end from Gemini. A start-only move could therefore silently replace 90 minutes with the model's guessed 60 minutes.
4. **Duration-preservation fix.** The server derives end from the canonical DB duration and new start. Model-generated end arithmetic is ignored for such moves, including an invented ambiguous DST end. Explicit numeric minute/hour duration or explicit end/range intent is parsed from the human request and bounded by the existing 720-minute maximum. Duration-only changes also derive end from canonical start. Expected version and canonical before state remain unchanged for Apply revalidation.
5. **Review again root cause.** A generic identity expression used `entityId ?? taskId ?? projectId`. A conflicted create has no persisted block ID, so it inserted the project ID as a time-block identifier.
6. **Review again fix.** Added an action-aware prompt builder. Create review uses title, available task/project labels, local date/time and duration, requests another verified slot, and asks for missing work hours. Update review refers to the existing block's title/date and requested new start, preserving current duration. Cancellation explicitly refers to cancelling the persisted block. Time-block composer text contains no UUIDs. Failed actions do not claim an unproven overlap diagnosis. Apply/Cancel payload construction is unchanged.
7. **HTTP 400 root cause.** Reproduced a concrete provider/schema mismatch during a normal live move: `list_time_blocks` received string `startAt`/`endAt` values shaped as local `YYYY-MM-DDTHH:mm`, while its strict parser requires timestamps with seconds and an explicit offset. Metadata captured tool, field names/types and the `local-wall-time` category, without values. Previously, an `INVALID_INPUT` from model tool parsing escaped through the route as HTTP 400. The exact historical Find request's original arguments were never captured, so this report does not assert that its field mismatch was identical.
8. **Normalization/recovery behavior.** Normalize only equivalent clock spellings (`9:00`, `9 AM`, `3:00 PM`) into HH:mm. For read-range wall timestamps only, convert strict local YYYY-MM-DDTHH:mm using the authoritative workspace timezone and existing unique-round-trip DST validator. Strict parsers still run afterward. Invalid dates, ambiguous/nonexistent wall times, unexpected fields, missing fields, wrong types and invalid offsets remain rejected. Recoverable scheduling argument failures return a safe clarification with no drafts, including mixed read rounds and a later failure after earlier drafts. Unknown tools, provider failures, limits and unrelated phase behavior retain their existing error paths. Read-tool descriptions now state the timestamp format explicitly.
